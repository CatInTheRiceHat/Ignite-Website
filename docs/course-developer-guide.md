# The standard for an Ignite course week

Use the **Relationships, Boundaries & Social Skills, Week 1** demo as a concrete example. Run `npm run dev` and open [the sample week locally](http://127.0.0.1:5173/demo/boundaries). The routes below refer to that local site. See the [source map and deliberate adaptations](course-demo.md) before reusing its content.

| Standard | What a developer should demonstrate | Concrete example |
| --- | --- | --- |
| Clear objectives | Describe what students will be able to do, in observable terms. State prerequisites, workload and the work they will produce. | [Objectives and week outline](../src/data/demo/week.ts), with objectives shown in the first lesson and workload in the introduction. “Give an example of each boundary type” is supported by five required fictional examples in `?part=learn`. |
| Complete explanations | Teach enough for the week to stand alone. Define terms, explain why they matter, address likely misconceptions and provide a text path if media is unavailable. | [The lesson](../src/components/demo/Lesson.tsx) explains the five types, consent, context, boundaries versus control, and how to choose a next step. The optional video is not needed to complete the lesson. |
| Worked examples | Show the situation, the decision and the reasoning. Follow examples with a chance to apply the same idea. | [Four guided scenarios](../src/data/demo/week.ts) cover messages, late-night calls, copied homework and private grades. Students check an answer, read the explanation, then write their own examples. |
| Meaningful practice | Ask students to use the skill, not just click through pages. Provide support and optional stretch work without requiring personal disclosure. | [The Borrowed Hoodie](../src/components/demo/CaseStudy.tsx), `?part=case`, asks for story evidence, a protective limit, another perspective and a repair. Sentence starters, two challenges and a three-criterion self-review support revision. |
| Useful feedback | Explain the reasoning behind each choice. Offer a helpful hint, another attempt and clear keyboard focus. Keep first-check results distinct from results after review. | [Question feedback and retry behavior](../src/components/demo/Question.tsx). The [case feedback example](../src/components/demo/CaseStudy.tsx) explicitly distinguishes an authored model from live mentor feedback. |
| Accessible presentation | Use readable sections, labelled native controls, visible focus, announced feedback and navigation that works without hovering, dragging or color alone. | [Writing fields](../src/components/demo/Writing.tsx), [question navigation](../src/components/demo/Quiz.tsx), and [responsive styles](../src/components/demo/demo.css). On phones, a labelled part selector remains available while reading. |
| Aligned assessment | Check every stated skill. Include application as well as recall, and tell students how work is reviewed. Never mistake text length or a page visit for understanding. | [The final check](../src/data/demo/finalQuestions.ts), `?part=final`, includes all five boundary types and contextual decisions. The case and `?part=finish` Boundaries Map assess written application through explicit self-review criteria. |

Write explanations in connected, conversational prose, as in the opening of [the lesson](../src/components/demo/Lesson.tsx). Explain the idea and its reasoning instead of relying on slogans, strings of sentence fragments or repeated praise. Avoid em dashes and unnecessary hyphenation. Keep control labels concise and let fictional dialogue sound like something a person would actually say.

Use the shared [sample configuration](../src/config/courseDemo.ts) for a featured course's public details. Keep the [homepage feature](../src/components/program/FeaturedCourse.tsx) to its artwork, title, creator and sample link, with scope and workload explained inside the sample. The [learning timeline](../src/components/demo/LearningTimeline.tsx) takes its entries from the actual week outline, so another pathway can use the same presentation with different lessons and activities. Keep the featured promotion separate from each sample's permanent URL and saved progress. See the [rotation instructions](course-demo.md#monthly-feature-and-reusable-introduction) before adding a new sample.

Before handing over a week, complete it as a new student: try wrong answers, use feedback, revise writing, refresh, revisit, download and reset. Test keyboard use and narrow screens. Confirm every link and required asset, and check that progress changes only when related work changes. The [browser checks](../tests/sol/browser/course-demo.spec.ts) demonstrate these paths; automated accessibility scans support, but do not replace, assistive-technology testing.

Preserve source meaning and workload, and record substantial adaptations. Use fictional public examples; exclude student submissions, private contact details and instructor-only notes. Explain the limits of self-review and browser-local saving. A polished opening page cannot compensate for missing lessons, vague activities or feedback that only says “wrong.”
